# 数据清洗与增量接入规则

本规范适用于英文尼泊尔徒步问答原型。第一批只使用 R03 冻结审核版中已接受的六条事实：`K07`、`K08`、`W01`–`W04`。K09 已排除，K01–K06 的距离字段暂停；W05–W06、P01–P02 等待审事实不因开始开发而自动接受。冻结源文件不在本项目中修改。

## 1. 四层数据边界

| 层 | 内容 | 能否进入检索 |
| --- | --- | --- |
| 原始与审核历史 | 原网页快照、GPX/CSV、版本观察、冲突、验收日志 | 否 |
| staging | 新来源、提取候选、待核实体、许可或内容尚未确认的记录 | 否 |
| release | 逐条接受、来源范围明确、内容哈希匹配且列入发布清单的事实与来源元数据 | 是，仅白名单字段 |
| evaluation | 问题、参考答案、评分标准、人工评分、实验输出 | 否 |

禁止扫描整个项目目录构建知识库。读取入口必须是一个明确的 release manifest；允许的检索内容仅为事实陈述、限定、参考版本上下文和必要来源归属。审计文字不是补充知识库，不能用来绕过字段暂停决定。

## 2. 来源准入

每个来源至少登记：稳定 `source_id`、标题、发布者、原文 URL、定位、版本或修订 ID、观察日期、许可链接及适用范围、署名、来源链和取得限制。观察日期不等于内容生效日期；网页读取器的缓存时间不证明源站最新。

官方身份、使用许可和事实质量分别判断。官方来源适合核查管理规则及官方发布值，但未必与某个私人行程版本的起终点和测量口径匹配。非官方来源可以贡献可追溯的特定事实；同一发布者的多个页面不构成独立交叉验证。

首轮来源：O01 为 KeiTreks 选定发布字段（CC BY 4.0）；O03 为 Wikivoyage 选定走廊描述（CC BY-SA 4.0，并保留其导入作品提示和贡献历史）。两者的许可不能扩展为整站图片、其他页面或全部链接材料的授权。`data/release/ATTRIBUTION.txt` 必须随对应资料保留。

## 3. 提取、清洗与校验

1. **取得证据。** 使用正常公开访问保存允许的来源版本与字节哈希；无法取得固定版本时，明确记录仅观察到渲染正文与修订 ID，不伪称原始归档已经完成。
2. **按字段提取。** 一条事实只表达一个可审核关系或数值。原文位置与提取依据分开保存；英文改写不能扩大原文含义。路线长度、海拔、累计爬升、时间、发布日期和录制日期不能混用。
3. **绑定参考对象。** 区分完整行程、日段端点、走廊关系、支线访问和地点元数据。Siwai 返回参考不等于 Nayapul 接近路线；日段端点列表也不是所有途经点或精确几何。
4. **处理实体。** 保留来源拼写；不得仅凭字符串相似合并 Chimrong 与 Chomrong。营地、旅馆、观景点与轨迹采样点分别建模。南侧 Sanctuary ABC 不自动等同于 North ABC。
5. **规范单位。** 数值与单位分栏，保留 `original_display`、原始精度和归一化说明。近似值保持近似；未知测量基准保持未知。两个点高程之差不是累计爬升。
6. **查重与冲突。** 相同来源链的转载去重，但保留出处。不同边界或口径先分版本，不平均或多数投票选数。无法解释的关键指标进入隔离层；使用决定可以暂停字段而不销毁历史。
7. **绑定验收。** 新增或改变事实正文、限定、来源依赖及许可范围，须生成新 revision / 内容哈希并重新验收。格式合法、许可证标签或自动检查通过都不能代替人的事实接受。

## 4. Chunk 与 embedding

首批是六条短事实，采用“一条事实一个 chunk”，不为增加数量拆成碎片，也不使用跨事实 overlap。chunk 带有 `fact_id`、内容哈希、参考版本、原文定位、来源与许可。派生 chunk 的 ID/哈希与来源事实的审核哈希分别记录。

后续长文先按标题、路线版本和语义边界划分，再以约 200–350 tokens 的候选窗口实验；30–50 tokens 的 overlap 只是待比较配置，不是首轮已经验证的最优值。不得把多个路线版本或数据与评估答案放进同一个 chunk。

语义检索采用 Qwen3-Embedding-0.6B。索引须记录模型 ID / revision、向量维度、归一化方式、chunk 版本和 release 哈希；查询与文档必须采用匹配配置。更换 embedding 或维度需建立新索引，不能继续使用旧向量。离线词汇检索可用于程序检查与证据预览，但必须显式标示，不能冒充该 embedding 模型的实验结果。

## 5. 接入新资料的流程

```text
新来源 → 许可与来源登记 → staging 提取 → 字段/实体/版本清洗
       → 冲突与依赖检查 → 人工验收 → 新 release manifest
       → 生成派生 chunks → 新索引或受控更新 → 开发题回归 → 人工验收
```

新资料可以沿同一结构接入，JSONL 不设六条或十六条上限；但“可扩展”不表示“自动准入”。新增 stable ID 不回收旧 ID。旧值被修正时，保留旧 revision 与排除原因；内容变化触发对应验收失效。

小型试点优先完整重建派生索引，减少残留旧 chunk 的风险。资料增多后才考虑按内容哈希 upsert、删除旧 revision，并以新的 manifest / collection 切换；切换前检查条目数、来源许可、停用字段和检索回归。回滚选择上一版数据与匹配索引，不覆盖冻结原文。

### 本地命令与人工交接

在项目目录、安装项目依赖后，可先生成候选文件：

```sh
python scripts/stage_update.py --facts incoming.jsonl --output "$HOME/Library/Caches/Trailwise/nepal-trail-rag/model-runtime/staging/review-02"
```

命令只清理 `statement_en` 与 `qualification_en` 的 Unicode 兼容形式和多余空白；不自动改测量值、单位、地名实体或来源引用。默认对照当前 `data/release`，已存在事实的内容变化使 revision 增加一；未来可通过 `--base-release` 指定上一份已验证发布版。输出始终标记 `PENDING`，不生成可激活的 manifest。`cleaning_log.audit.json` 记录变化与哈希，不能进入检索。

人审时同时核对候选、原文、来源权利和引用版本。接受后，事实本身的 `review.reviewed_content_sha256`、`content_sha256` 与人工事件的 `accepted_content_sha256[fact_id]` 必须一致；来源也必须有匹配的权利审查哈希。事件须包含 event ID、reviewer、reviewed_on 和明确的 `confirmed_by_human: true`。该声明记录人工决定，软件不能自行判断声明是否真实，也不会替用户写下实际接受。

确认完成后才创建新发布目录：

```sh
python scripts/promote_release.py --facts reviewed.jsonl --sources reviewed_sources.jsonl --scope scope.json --review-event review_event.json --output data/releases/review-02 --release-id NEPAL-LOCAL-REVIEW-02
```

这里的文件名是操作示例，不代表已有审核。命令只保留事实实际引用的来源，沿用其原 payload 和署名；将完整人工事件存为不参与检索的 `review_event.audit.json`，并纳入文件哈希。临时目录通过与应用相同的完整加载校验后才成为新目录；任何失败都不产生发布版，已有目录不覆盖，也不自动切换应用。

K09 始终为 excluded，K01–K06 始终为 suspended，并继承本轮事件新增的停用 ID；这个 CLI 不支持恢复它们。未来如有充分依据恢复，需要另行定义明确的重新授权流程。当前最小原型也拒绝带有 conflict `bundle_ids` 的事实；支持冲突包整体审核与检索前，应先扩展依赖校验和相应测试。

## 6. 本轮限制

目前六条只支持参考行程天数、日段端点及社区走廊顺序。它们不能证明已收齐超过 10 km 的完整测量路线，也不能支持个性化风险适配、实时天气、当前通行或事故减少效果。之后应按有价值的问题补齐新路线资料，不重新启用已经暂停的数字来填空。
