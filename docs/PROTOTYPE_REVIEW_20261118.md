以下是对原始输出的初步诊断，不是已接受的人工成绩。失败样例保留在采集目录，不用修改原始答案的方式美化成绩。

按当前required-fact标注，D01/D02/D03/D04的必需事实全部进入top-3，D06为1/2，D08为2/3。这只是检索诊断，尤其D08的标注仍需人审；不是回答准确率。人工需要逐断言检查引用和版本边界。

## 效率记录与解释范围

同一轮事实题每组6次请求，客户端端到端耗时中位数：RAG约9.56秒，基线约7.88秒；RAG范围约6.35–20.86秒，基线约3.47–11.24秒。输出长度不一致，调用顺序交替且存在本地缓存，所以这组小样本不能证明稳定的速度差异。边界规则的近即时响应未混入这些数值。

首次环境曾放在iCloud管理的Documents中，依赖按需读取导致很长等待。现在实际运行环境和固定模型使用 `~/Library/Caches/Trailwise/nepal-trail-rag/`，源资料和审核发布记录仍按项目目录管理。旧生成目录保留作恢复副本，不是当前运行入口；清理前先核对新缓存与本轮实现验收。Caches属于可重建资料，不可作为唯一的人工审核记录保存地。

本轮验证了模型和embedding能同时运行，但没有测得完整GPU/统一内存峰值。单次进程RSS不包含完整Metal内存，不能用它宣称整个系统只占不到1GB。峰值内存、长上下文和持续负载测试留作后续效率实验。

## 下一轮先做什么

建议用户先验收：资料是否仅含已接受条目；页面能否查看原文与许可；有/无RAG是否用同一模型配置；上述错误诊断与待评分表是否清楚。用户接受本轮实现后，再记录实现版本与代码提交；事实接受与实现验收分别保存。

下一轮只测试一个假设：**把已接受的有序端点显示为明确的Day / start / finish派生表，能否减少日段偏移？** 保留原事实payload和哈希，先逐项核对派生规则与映射，再改变chunk格式、生成新索引，复跑同题；是否有效以及是否增加其他错误都保留。不要同轮同时改模型、prompt和top-k。

后续分轮安排：

1. 检索召回实验：固定其余配置比较top-k，或给定正确上下文做独立的oracle诊断，分开识别检索与生成错误。
2. 开发协议人审：核对critical errors与required facts；修订题目时保留旧协议、旧原始结果及修订原因。
3. 未见题：加入自然英语问题和新增证据单元，减少对自定义版本ID的依赖；避免用开发题成绩宣称泛化能力。
4. 效率与范围扩展：测真实内存峰值、稳定延迟、故障和新增数据回归，再逐批加入有许可及足够证据的资料。
